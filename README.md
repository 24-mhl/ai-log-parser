# ai-log-parser

把 Web 访问日志交给大模型，做一次**应急初筛**：谁在打、什么时候、打了哪里、有没有得手。

目标不是让模型替代分析，而是把「206 行日志里先看哪几条」这件事从十分钟压缩到十秒，剩下的判断仍然靠人。

## 用法

```bash
cp .env.example .env                             # 填入 ZHIPU_API_KEY
python -m ai_log_parser access.log -o report.md  # 日志进，报告出
```

| 参数 | 作用 |
|---|---|
| `-o report.md` | 把 markdown 报告写到文件；不给就打到终端 |
| `--dry-run` | 只做预筛、打印将要发送的 prompt，不发请求、不花额度 |
| `--max-lines 20` | 最多送多少条候选行给模型 |
| `--per-ip 4` | 每个 IP 最多保留几种请求形态（有得手的 IP 自动多给 2 个名额） |
| `--json out.json` | 把模型返回的原始 JSON 另存一份 |
| `--model glm-4-flash` | 换模型，默认读环境变量 `GLM_MODEL` |

```bash
python -m unittest discover -s tests    # 13 个离线测试，不联网
```

## 它做了什么

| 步骤 | 模块 | 关键点 |
|---|---|---|
| 1. 解析 | `reader.py` | 正则按「引号整体」匹配。用 `split()` 的话，UA 里的空格会把状态码的位置挤歪 |
| 2. 预筛 | `prescreen.py` | 规则打分，206 行压到 15 条。同一 IP 的同一形态只留一条，次数单独统计 |
| 3. 调模型 | `llm.py` | 只喂统计表 + 候选行，要求返回 JSON |
| 4. 核对 | `sanitize.py` | 模型编的 IP、编的行号、抄回来的占位符，在这里被剔除 |
| 5. 渲染 | `report.py` | 出 markdown，附统计表和候选行清单，便于逐条复核 |

## 输出样例

`report.md` 的前半部分（完整样例在仓库里）：

```markdown
| 原始行数 | 206 |
| 送入模型 | 15 条候选行 |
| token | 输入 2304 / 输出 340 |

## 一、结论
**最可疑来源**：`198.18.44.91`

## 二、时间线
| 时间 | 行号 | 事件 |
| 02:04:02 | L8 | 认证被拒 |
| 02:24:39 | L35 | 敏感路径访问 |
| 02:25:02 | L37 | 敏感路径访问 |

## 三、逐个来源判定
| IP | 判定 | 证据行 | 理由 |
| `198.18.44.91` | 得手 | L35、L36、L37、L39 | 访问敏感路径并成功 |
| `203.0.113.77` | 零得手 | L44、L45、L61、L78 | 尝试访问敏感路径并失败 |
```

## 实测：一次样本的前后对比

样本是一份 206 行的应急靶场 access.log（9 个来源 IP，其中 1 个真攻击者、1 个扫描器、1 个忘密码的员工）。

| 指标 | v0.1（整份喂） | v0.2（预筛 + 校验） |
|---|---|---|
| 输入 token | 18393 | 2304 |
| 模型编造行号 | 有（报了个不存在的「第 198 行」） | 无（行号由脚本给，编的会被剔除） |
| 扫描器误判 | 列为「危险程度高」 | 正确标为「零得手」 |

## 设计取舍

**只用标准库。** 这台机器 `pip` 走代理会 502，装 `requests` 反而多一道坎；`urllib` 够用，换台机器直接能跑。

**四问固定写死。** 每次问法不一样，结果就没法横向比较。

**不让模型报行号。** 早期版本要求它「引用具体行号」，结果它开始虚构 —— 报了个「第 198 行」，实际那一行是完全无关的请求。现在行号由脚本在候选行前面标好，模型只能从里面挑，挑错了会被 `sanitize` 剔掉。

**不指望模型数数。** 它会把「38 次全失败的扫描器」和「22 次爆破后登录成功」排在同一档，因为差别只在**次数**。次数由脚本算，模型只负责把算好的指标写成叙述。

**同一形态只留一条。** 某个 IP 对着登录页撞了 22 次，喂 22 行没有意义 —— 模型要的是形态，不是次数。

**302 必须留在候选里。** 哪怕它分数不高。那是「进去了」的唯一证据，被分数挤掉就等于丢结论。

**校验层不是补丁，是分工。** 模型的职责是写叙述，事实核对归脚本。要求「prompt 写得够好，模型就不会编」是幻想，实测三次都编。

**温度压到 0.2。** 分析类任务不需要创造力。

## 目录结构

```
.
├── ai_log_parser/          # v0.2 包，入口 __main__.py
│   ├── reader.py           #   解析
│   ├── prescreen.py        #   打分与挑选
│   ├── llm.py              #   调模型、抠 JSON
│   ├── sanitize.py         #   用脚本事实核对模型输出
│   └── report.py           #   渲染 markdown
├── tests/test_core.py      # 13 个离线测试
├── report.md               # 输出样例
├── api.py                  # v0.1 单文件版，留作对照
├── stats.py                # 单文件统计脚本
└── practice.py             # 手写练习稿（照着教程一步步敲的那版）
```

`api.py` / `stats.py` / `practice.py` 是 v0.1 时代的单文件版本，功能已被包内模块覆盖。留着是因为迭代过程在里面：`practice.py` 能看到三次 prompt 改动，`api.py` 能看到没有预筛时长什么样。

## 注意

- `.env` 已被 `.gitignore` 挡住，**不要把 Key 提交进仓库**
- 真实日志里可能有内网 IP、账号、URL 参数（含 token），发给模型前先评估是否脱敏
- 免费模型有速率限制，连续跑多条日志时加间隔，不然会撞 429
- 报告里的每条判定都要回到原始日志对应行复核 —— 「得手」只代表登录成功过，不等于它一定是攻击者
