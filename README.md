# ai-log-parser

把 Web 访问日志交给大模型，做一次**应急初筛**：谁在打、什么时候、打了哪里、有没有得手。

目标不是让模型替代分析，而是把「206 行日志里先看哪几条」这件事从十分钟压缩到十秒，剩下的判断仍然靠人。

## 用法

```bash
cp .env.example .env          # 填入 ZHIPU_API_KEY
python api.py access.log      # 出报告
```

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只打印将要发送的 prompt，不发请求、不花额度 |
| `--max-chars 6000` | 日志太长时截断（按行截，不会切断状态码）；默认 50000，够放 206 行的典型 access.log |
| `--json out.json` | 把原始响应存下来，方便对比不同模型 |
| `--model glm-4-flash` | 换模型，默认读环境变量 `GLM_MODEL` |

## 设计取舍

**只用标准库。** 这台机器 `pip` 走代理会 502，装 `requests` 反而多一道坎；`urllib` 够用，换台机器直接能跑。

**四问固定写死。** 每次问法不一样，结果就没法横向比较。四问是：谁在打 / 什么时候 / 打哪里 / 有没有得手，并要求给出行号依据。

**禁止模型编。** 系统提示里明确：只根据日志回答，看不出来就写「日志中无法判断」。长日志里模型的编造倾向会明显上升，所以 v0.1 先把「不猜」这条按住。

**温度压到 0.2。** 分析类任务不需要创造力。

## 路线图

- [x] **v0.1** 读日志 → 调模型 → 四问报告
- [ ] **v0.2** 正则预筛：先用规则挑出可疑的 20 条，只喂这些（省 token、也更准）
- [ ] **v0.3** 输出改 JSON，便于下游解析和汇总
- [ ] **v0.4** 多条日志批量跑，出对比表

## 注意

- `.env` 已被 `.gitignore` 挡住，**不要把 Key 提交进仓库**
- 真实日志里可能有内网 IP、账号、URL 参数（含 token），发给模型前先评估是否脱敏
- 免费模型有速率限制，连续跑多条日志时加间隔，不然会撞 429
